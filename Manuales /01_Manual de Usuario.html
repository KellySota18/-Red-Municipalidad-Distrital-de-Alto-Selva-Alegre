2. Introducción y descripción del sistema

2.1 Problema que atiende

La red de la Municipalidad Distrital de Alto Selva Alegre creció sin un inventario centralizado y sin una política de segmentación verificable. En la documentación de origen se identificaron, entre otros, los siguientes problemas:

  • No existe un registro único y ordenado de sedes, VLAN, subredes, equipos, marcas, modelos, estados, ubicaciones e interfaces.
  • Los mantenimientos se coordinan de forma verbal o dispersa; no hay trazabilidad de quién los realizó ni cuándo vence el siguiente.
  • La red actual es plana (sin VLAN) y el diseño propuesto (VLAN 10, 20, 30, 40, 50 y 99) no se puede validar antes de aplicarlo.
  • Las listas de control de acceso (ACL) del informe se aplicaron con una postura de “permitir por defecto”, lo que deja pasar tráfico no autorizado.
  • No hay evidencia reproducible de las pruebas de conectividad ni un registro de los cambios realizados.

2.2 Objetivo principal

Proporcionar a la municipalidad un sistema seguro, ordenado y reproducible para inventariar la red, gestionar los mantenimientos, administrar usuarios con roles y probar las ACL antes de aplicarlas, dejando auditoría de cada cambio.

2.3 Objetivos específicos

  1. Centralizar el inventario de ubicaciones, VLAN, subredes, dispositivos e interfaces.
  2. Registrar y dar seguimiento a los mantenimientos preventivos, correctivos y de inspección.
  3. Aplicar autenticación, roles y permisos directamente en la base de datos.
  4. Simular y comparar las ACL del informe (v1) con una propuesta de denegación por defecto (v2).
  5. Generar configuraciones IOS y un plan de pruebas para Cisco Packet Tracer.
  6. Mantener una bitácora inmutable y copias de seguridad cifradas.

2.6 Tipo de solución desarrollada

El sistema es una solución de escritorio basada en consola (CLI) compuesta por tres capas:

  1. Cliente de consola: PowerShell 5.1 o 7 con el módulo RedCli.psm1.
  2. Servicio web (API REST): Node.js 20 con Express, que valida, autentica y autoriza.
  3. Base de datos: PostgreSQL 16 con el esquema infra, reglas de integridad, RLS y auditoría.

Adicionalmente incluye herramientas de línea de comandos en Node.js para simular ACL, generar configuraciones IOS y producir un plan de pruebas para Cisco Packet Tracer.

Importante: esta versión no tiene interfaz web ni aplicación móvil. La “pantalla” del usuario es la consola de PowerShell. La API se consume desde la consola y no está pensada para ser abierta directamente en un navegador. La administración avanzada de la base se realiza con pgAdmin 4.

2.7 Alcance y limitaciones

El sistema sí hace El sistema no hace
Inventario de sedes, VLAN, subredes, dispositivos e interfaces Monitoreo en tiempo real ni alertas de caída
Mantenimientos con responsable, fechas y estados Configurar routers o switches por sí solo
Usuarios, roles, sesiones, bloqueo y auditoría Autenticación en dos pasos (MFA)
Simulación y pruebas de ACL v1 y v2 Simular NAT/PAT ni el estado real de TCP
Generación de configuración IOS y plan para Packet Tracer Sustituir al firewall FortiGate real
Copias de seguridad cifradas y prueba de restauración Recuperación de contraseña por correo
Interfaz de consola y API REST Interfaz web o aplicación móvil

Otras limitaciones conocidas:

  • Las ubicaciones, interfaces, enlaces y parte del diseño se registran con SQL en pgAdmin; la consola registra dispositivos, mantenimientos y usuarios.
  • Los equipos del Diario no tienen fecha de instalación ni IP de servidor confirmada, por lo que algunas listas aparecen vacías al inicio.
  • Los scripts de Windows (copias de seguridad, tarea programada, BitLocker) siguen la documentación estándar, pero no se probaron exhaustivamente en Windows.
  • El simulador de ACL comprueba la lógica de las listas, no la sintaxis exacta de cada versión de Packet Tracer.

3.6 Requisitos de acceso, registro o autenticación

  • El acceso es solo por invitación: no existe registro público de usuarios.
  • Un administrador crea la cuenta y entrega una contraseña temporal por un canal seguro.
  • El correo debe ser institucional y único.
  • La contraseña debe tener 12 o más caracteres, con mayúscula, minúscula, número y símbolo, y un máximo de 72 bytes.
  • La cuenta se bloquea 15 minutos tras 5 intentos fallidos consecutivos.
  • La sesión se cierra automáticamente tras 30 minutos de inactividad o a las 8 horas de su creación.
  • La sesión se invalida de inmediato si la cuenta se desactiva o si se cambia la contraseña.

4. Acceso e inicio de sesión

4.1 Dirección web o procedimiento para abrir la aplicación

No hay una página web de inicio de sesión. El acceso se realiza desde PowerShell contra la dirección de la API que indique el administrador:

Entorno Dirección de ejemplo
Desarrollo local http://127.0.0.1:3000
Servidor de pruebas http://servidor:3000
Producción institucional https://red.altoselvaalegre.gob.pe

El administrador debe entregar al usuario:

  1. La dirección exacta de la API.
  2. Su correo institucional.
  3. Su contraseña temporal.
  4. La ruta donde está instalado el proyecto (por ejemplo, C:\proyecto_red).

4.2 Preparación de la consola (solo la primera vez)

  1. Instalar PowerShell 7 si no está disponible:

powershell winget install Microsoft.PowerShell

  1. Abrir PowerShell 7 desde el menú Inicio.
  2. Permitir la ejecución de scripts firmados o locales, solo para el usuario actual:

powershell Set-ExecutionPolicy -Scope CurrentUser RemoteSigned

  1. Cargar el módulo del sistema:

powershell Import-Module C:\proyecto_red\scripts\RedCli.psm1 -Force

  1. Comprobar que los comandos están disponibles:

powershell Get-Command -Module RedCli

Resultado esperado: una lista que incluye Connect-Red, Disconnect-Red, Get-RedDispositivo, Get-RedVlan, Get-RedSubred, Get-RedMantenimiento, entre otros.

Cada vez que se abra una ventana nueva de PowerShell se debe repetir el paso 4. Si se cierra la ventana, la sesión y el módulo se pierden.

4.3 Registro de nuevos usuarios

No existe auto-registro. El procedimiento es:

  1. El usuario solicita el alta al administrador del sistema por el canal institucional.
  2. El administrador verifica la identidad y el rol que corresponde.
  3. El administrador ejecuta New-RedUsuario (ver sección 6.13) y entrega la contraseña temporal por un canal seguro, nunca por correo masivo ni mensajería pública.
  4. El usuario inicia sesión y cambia la contraseña en el primer ingreso con Set-RedContrasena (ver sección 6.12).

4.4 Inicio de sesión

  1. Abrir PowerShell 7.
  2. Cargar el módulo:

powershell Import-Module C:\proyecto_red\scripts\RedCli.psm1 -Force

  1. Ejecutar el comando de conexión, reemplazando la dirección y el correo por los datos entregados:

powershell Connect-Red -Url http://127.0.0.1:3000 -Correo su.nombre@altoselvaalegre.gob.pe

  1. Escribir la contraseña cuando se solicite. No se muestra nada en pantalla mientras se escribe; es el comportamiento normal de PowerShell por seguridad.

Evidencia de consola:

Figura 1. Inicio de sesión correcto. La columna Rol debe coincidir con el rol asignado.

Resultado esperado: se muestra el identificador del usuario, su rol y la dirección del servidor. Si el rol mostrado no es el esperado, el usuario debe detener el trabajo y comunicarse con el administrador.

Errores frecuentes al iniciar sesión:

Mensaje Significado Acción
Correo o contraseña incorrectos… Algún dato está mal, la cuenta está desactivada o bloqueada Revisar mayúsculas, teclado y correo. Tras 5 fallos, esperar 15 minutos o pedir al administrador que restablezca
No se pudo contactar con el servidor… La dirección es incorrecta o la API está apagada Verificar la dirección con el administrador y que el servicio esté activo
Demasiados intentos… Se superó el límite de intentos Esperar unos minutos
No se encontró el token de seguridad (CSRF)… La sesión no se estableció correctamente Volver a ejecutar Connect-Red

4.5 Recuperación de contraseña

La versión 1.0 no envía correos de recuperación y no permite el autoservicio. El procedimiento es:

  1. El usuario comunica al administrador que olvidó su contraseña o que su cuenta está bloqueada.
  2. El administrador verifica la identidad del usuario por un canal institucional.
  3. El administrador restablece la contraseña y desbloquea la cuenta mediante el procedimiento administrativo de la base de datos (ver manual de instalación, anexo D).
  4. El administrador entrega una contraseña temporal por un canal seguro.
  5. El usuario inicia sesión y la cambia de inmediato con Set-RedContrasena.

Si la cuenta está bloqueada por 5 intentos fallidos, el desbloqueo automático ocurre a los 15 minutos. Si el usuario no recuerda la contraseña, el restablecimiento debe hacerlo un administrador.

4.6 Cierre de sesión

  1. Ejecutar:

powershell Disconnect-Red

  1. Verificar el mensaje “Sesión cerrada.”

Evidencia de consola:

Figura 2. Cierre de sesión correcto. Después del cierre, los comandos de consulta exigen una nueva conexión.

Resultado esperado: la sesión se invalida también en el servidor. Si se intenta consultar sin sesión, el sistema responde “No hay sesión activa…”.

Cerrar la ventana de PowerShell no siempre invalida la sesión en el servidor; por eso se debe usar siempre Disconnect-Red, especialmente en equipos compartidos.

5. Descripción de la interfaz

5.1 Naturaleza de la interfaz

La interfaz del sistema es una consola de comandos. No hay botones, ventanas ni formularios gráficos. Cada “pantalla” es la salida de un comando y cada “formulario” es el conjunto de parámetros del comando.

Elemento de una interfaz gráfica Equivalente en este sistema
Pantalla principal Ventana de PowerShell con el módulo cargado y la sesión iniciada
Menú de navegación Lista de comandos disponibles según el rol
Formulario Parámetros del comando (-Nombre, -Tipo, -Fecha, etc.)
Botón Aceptar Tecla Enter después de escribir el comando
Botón Cancelar Ctrl + C para interrumpir un comando
Campo obligatorio Parámetro marcado como [Parameter(Mandatory)]; PowerShell lo solicita si falta
Ayuda en línea Get-Help <comando> -Examples
Mensajes y notificaciones Texto devuelto por el comando o por el manejador de errores de RedCli

5.2 Pantalla principal

La pantalla principal es la ventana de PowerShell. En ella se distinguen:

  • Prompt: indica la ruta actual, por ejemplo PS C:\proyecto_red>.
  • Comando: línea que empieza con el nombre del comando (Connect-Red, Get-RedDispositivo, etc.).
  • Salida: tabla o lista con los datos solicitados.
  • Mensajes: texto informativo o de error.

6. Procedimientos de uso de las funcionalidades

Convención: los ejemplos usan datos de demostración. Reemplace correos, UUID, fechas y nombres por los de su institución. No copie contraseñas de ejemplo en producción.

6.1 Consultar todos los equipos (inventario)

Propósito: obtener la lista completa de dispositivos registrados.
Requisitos previos: sesión iniciada.
Rol: Consulta, Técnico o Administrador.

Procedimiento:

  1. Verificar la sesión con Get-RedYo.
  2. Ejecutar:

powershell Get-RedDispositivo | Format-Table Nombre, Tipo, Estado, Piso -AutoSize

  1. Para ver todas las columnas disponibles:

powershell Get-RedDispositivo | Format-List

Evidencia de consola:

Figura 4. Consulta de equipos filtrada por tipo servidor.

Resultado esperado: una tabla con los equipos, su tipo, estado y piso. La cantidad inicial documentada es de 15 dispositivos.

Notas:

  • Si no ve ningún equipo, verifique que la sesión esté activa y que la API esté funcionando.
  • La lista está limitada a 200 registros por consulta en la API.

6.2 Filtrar equipos por tipo, estado o nombre

Propósito: localizar rápidamente un equipo o un grupo de equipos.
Requisitos previos: sesión iniciada.
Rol: Consulta, Técnico o Administrador.

Procedimiento:

  1. Filtrar por tipo:

powershell Get-RedDispositivo -Tipo servidor | Format-Table Nombre, Tipo, Estado, Piso -AutoSize

  1. Filtrar por estado:

powershell Get-RedDispositivo -Estado averiado

  1. Buscar por parte del nombre:

powershell Get-RedDispositivo -Nombre FW

  1. Combinar con las órdenes de PowerShell:

powershell Get-RedDispositivo | Where-Object Piso -eq 4 | Sort-Object Nombre | Format-Table Nombre, Tipo, Estado

Resultado esperado: solo los equipos que cumplen el filtro. Los tipos y estados válidos son los de la tabla 5.4.

Notas:

  • El parámetro -Nombre no distingue mayúsculas de minúsculas y acepta coincidencias parciales.
  • Si escribe un tipo o estado no válido, PowerShell rechaza el comando antes de enviarlo a la API.

6.7 Consultar los próximos vencimientos

Propósito: anticipar los mantenimientos que vencen según la periodicidad de cada equipo.
Requisitos previos: sesión iniciada.
Rol: Consulta, Técnico o Administrador.

Procedimiento:

Get-RedMantenimiento -Proximos | Format-Table Dispositivo, UltimoMantenimiento, Proximo

Resultado esperado: lista ordenada de equipos con la fecha del último mantenimiento completado (o de instalación) y la fecha del próximo.

Cómo se calcula:

Próximo = (último mantenimiento completado o fecha de instalación)
          + periodicidad del equipo (por ejemplo, 12 meses)

Nota: si la lista aparece vacía al inicio, no es un error. Se llena cuando un equipo tiene fecha de instalación o un mantenimiento completado. Avise al administrador si falta esa información.

6.8 Programar un mantenimiento

Propósito: registrar un trabajo futuro y dejar constancia de que usted es el responsable.
Requisitos previos: sesión iniciada con rol Técnico o Administrador; conocer el nombre exacto del equipo.
Rol: Técnico o Administrador.

Procedimiento:

  1. Consultar el nombre exacto del equipo:

powershell Get-RedDispositivo | Format-Table Nombre, Tipo, Estado -AutoSize

  1. Programar el mantenimiento:

powershell New-RedMantenimiento -Dispositivo FW-FORTIGATE-90G ` -Descripcion 'Revision anual: limpieza, actualizacion de firmware y respaldo de configuracion' ` -Fecha 2026-12-10

  1. Guardar el Id que devuelve el sistema; lo necesitará para actualizarlo.

Evidencia de consola:

Figura 9. Mantenimiento programado correctamente.

Resultado esperado: un objeto con Id, Dispositivo, Programada y Estado = programado.

Reglas:

  • -Dispositivo: nombre exacto o UUID.
  • -Fecha: formato AAAA-MM-DD; otro formato se rechaza.
  • -Tipo: preventivo (por defecto), correctivo o inspeccion.
  • -Descripcion: entre 3 y 1000 caracteres, sin < ni >.
  • El responsable es siempre quien tiene la sesión; no se puede indicar a otra persona.

Propósito: reflejar el avance real del trabajo y recalcular el próximo vencimiento.

  1. Si se cancela:

powershell Set-RedMantenimiento -Id 53e2cf8e-bc10-4c3f-bd65-9b06c30849c9 -Estado cancelado

Evidencia de consola:

Figura 10. Mantenimiento marcado como completado con su fecha real.

Resultado esperado: el objeto actualizado con Id, Estado y Realizada.

Notas:

  • Solo puede cambiar sus propios mantenimientos. Si intenta cambiar el de otra persona verá “No se encontró el registro, o su rol no puede verlo”.
  • Al completar un mantenimiento, el sistema recalcula el próximo vencimiento de ese equipo.
  • Si el estado es completado y falta -FechaRealizada, la consola lo rechaza antes de enviar la solicitud.

6.12 Cambiar la propia contraseña

Propósito: reemplazar la contraseña temporal o una contraseña comprometida.
Requisitos previos: sesión iniciada.
Rol: Todos.

Procedimiento:

Set-RedContrasena
  1. Escribir la contraseña actual (no se muestra).
  2. Escribir la nueva contraseña (no se muestra).
  3. Confirmar el mensaje “Contraseña cambiada. Se cerraron sus sesiones: ejecute Connect-Red otra vez.”

Requisitos de la nueva contraseña: 12 o más caracteres, con mayúscula, minúscula, número y símbolo; máximo 72 bytes.

Ejemplo de construcción segura: piense en una frase y transfórmela, por ejemplo “Mi hijo nació en Arequipa en 2015” → Mh-nacio-en-AQP-2015!. No use ese ejemplo; cree uno propio y único.

Resultado esperado: todas las sesiones del usuario se revocan y debe volver a conectarse con Connect-Red.

6.13.3 Funciones administrativas no expuestas en la consola 1.0

El cambio de rol, la desactivación de una cuenta y el restablecimiento de contraseña no están expuestos como comandos de RedCli en la versión 1.0. Limitación documentada: si la institución necesita estas operaciones desde la consola, deben agregarse como nuevos comandos y rutas de API en una versión posterior.

6.15 Ejecutar las pruebas de ACL (rol Administrador / responsable de red)

Propósito: comprobar que las ACL del informe (v1) y la propuesta de denegación por defecto (v2) cumplen las políticas P1–P8, y generar la configuración para Packet Tracer.
Requisitos previos: Node.js 20 instalado; carpeta acl del proyecto; opcionalmente PostgreSQL cargado para guardar resultados.
Rol: Administrador / responsable de red.

Procedimiento:

  1. Abrir PowerShell y ubicarse en la carpeta de ACL:

powershell cd C:\proyecto_red\acl

  1. Ejecutar las pruebas:

powershell node probar_acls.js

  1. Verificar que la última línea sea:

RESULTADO: TODAS LAS PRUEBAS ESPERADAS PASARON

  1. Si se modificó la matriz de políticas, regenerar la configuración:

powershell node generar_config.js node plan_pt.js

  1. Para guardar las ACL en la base de datos (requiere PostgreSQL y psql en el PATH):

powershell node cfg_a_sql.js R1-FORTINET v2_default_deny config\R1_v2_migracion.cfg | psql -U postgres -d infra_red_db -v ON_ERROR_STOP=1 -q node cfg_a_sql.js R1B v2_default_deny config\R1B_v2_migracion.cfg | psql -U postgres -d infra_red_db -v ON_ERROR_STOP=1 -q

Evidencia de consola:

Figura 14. Resultado exitoso del simulador de ACL: v1 permitía el 73,2 % de las combinaciones; v2 solo el 9,4 % autorizado por la matriz.

Resultado esperado: todas las pruebas de la Tabla 16 pasan; la comparación muestra la reducción de tráfico permitido y la postura “DENEGAR por defecto” en las ACL v2.

Notas:

  • El simulador comprueba la lógica de las ACL, no la sintaxis exacta de cada versión de Packet Tracer.
  • Las ACL v2 son sin estado; no sustituyen al firewall FortiGate real.
  • Antes de aplicar una configuración en un router real, respalde la configuración y pruébela primero en Packet Tracer.

7. Mensajes de error y solución de problemas

7.1 Diagnóstico general

Antes de reportar un problema, realice estas cinco comprobaciones:

  1. ¿La ventana de PowerShell tiene el módulo cargado? Ejecute Get-Command -Module RedCli.
  2. ¿La sesión está activa? Ejecute Get-RedYo.
  3. ¿La API responde? Abra otra consola y ejecute Test-NetConnection servidor -Port 3000.
  4. ¿La dirección y el correo son correctos? Revise mayúsculas y espacios.
  5. ¿La cuenta está bloqueada o desactivada? Consulte al administrador.

7.3 Procedimiento para reportar un incidente

  1. Anotar la fecha, la hora y el comando ejecutado.
  2. Copiar el mensaje de error completo (sin contraseñas).
  3. Indicar el rol de la cuenta y la dirección de la API.
  4. Enviar la información al responsable de seguridad y a soporte por el canal institucional.
  5. No reintentar más de 3 veces si el error es de autenticación, para no bloquear la cuenta.

8. Recomendaciones de uso

8.1 Seguridad de las credenciales

  1. La contraseña es personal e intransferible. No se comparte, no se anota en papeles a la vista y no se envía por mensajería.
  2. Use una contraseña diferente a la de otros sistemas.
  3. Cámbiela de inmediato si sospecha que alguien la conoce.
  4. No use la opción de “recordar contraseña” en equipos compartidos.
  5. El sistema nunca solicita la contraseña por correo, teléfono ni mensajería.

8.2 Seguridad de la sesión

  1. Cierre sesión con Disconnect-Red al terminar.
  2. No deje la sesión abierta en equipos compartidos.
  3. Bloquee Windows (Win + L) si se aleja del equipo.
  4. No use el sistema desde cibercafés, equipos sin antivirus o redes públicas.
  5. La sesión se cierra sola tras 30 minutos de inactividad, pero no dependa de ello.

8.3 Integridad de la información

  1. Verifique el nombre exacto del equipo antes de programar un mantenimiento.
  2. Use descripciones claras, con qué se hizo, por qué y cuál fue el resultado.
  3. No incluya contraseñas, claves, configuraciones completas ni datos personales en las descripciones.
  4. No marque un mantenimiento como completado si no probó el servicio.
  5. No modifique el estado de un equipo sin autorización; el técnico no puede editar equipos en la versión 1.0.
  6. Exporte los CSV solo a carpetas institucionales y elimínelos cuando ya no los necesite.

8.4 Buenas prácticas de mantenimiento

  1. Avisar a los usuarios afectados y acordar una ventana de mantenimiento.
  2. Respaldar la configuración del equipo antes de intervenirlo (copy running-config startup-config en Cisco).
  3. Tener a mano cómo revertir el cambio.
  4. Verificar las baterías de los UPS antes de intervenir equipos críticos.
  5. Probar conectividad, DHCP y acceso a servidores antes de marcar completado.
  6. Documentar el resultado en la descripción o en un nuevo mantenimiento.

8.5 Buenas prácticas de seguridad de red

  1. Probar las ACL primero en el simulador y en Packet Tracer; nunca aplicarlas directamente en producción sin respaldo.
  2. Aplicar los cambios de ACL desde la consola del equipo, no por Telnet/SSH, para no perder el acceso.
  3. Usar reload in 10 en equipos reales antes de un cambio riesgoso y reload cancel al confirmar que todo funciona.
  4. Revisar los contadores matches de la regla deny ip any any log para detectar intentos bloqueados.
  5. No publicar direcciones IP, planos de red ni configuraciones en canales abiertos.
  6. Cambiar la contraseña de VTP que aparece en el Diario de Ingeniería y retirarla de los documentos.

8.6 Copias de seguridad y continuidad

  1. Mantener copias diarias cifradas y una copia fuera del equipo.
  2. Probar la restauración al menos cada trimestre; una copia que nunca se restauró no es una copia.
  3. Guardar la clave privada GPG fuera del servidor (USB cifrado o caja fuerte) y no en la misma máquina.
  4. Documentar quién es el responsable de las copias y dónde se guardan.

8.7 Conducta y reporte

  1. Cada persona usa su propia cuenta; el sistema registra quién hizo cada cambio.
  2. reportar de inmediato: acceso extraño, contraseña expuesta, equipo perdido, datos que no corresponden a su rol o mensajes que pidan credenciales.
  3. No intentar saltar las restricciones de rol ni manipular la base de datos sin autorización.
  4. Respetar la confidencialidad de la información de la red municipal.

9. Preguntas frecuentes

¿Puedo ver quién cambió un dato?
No con el rol Consulta. La bitácora la revisa el administrador o el DBA.

¿Por qué no veo las IP de los servidores?
Porque el informe de origen no asigna una IP a cada servidor. Quedan pendientes de confirmar y registrar.

¿Por qué “próximos mantenimientos” está vacío?
Porque se calcula desde la fecha de instalación o el último mantenimiento completado, y los equipos iniciales no tienen ninguno de los dos.

¿Puedo usar el sistema desde mi casa?
Solo si la institución habilita el acceso por VPN o publica la API con HTTPS y su equipo cumple los requisitos de seguridad.

¿Puedo crear mi propia cuenta?
No. El registro público no existe; un administrador debe crear la cuenta.

¿Puedo recuperar mi contraseña por correo?
No en la versión 1.0. El administrador la restablece y entrega una temporal por un canal seguro.

¿Qué pasa si fallo 5 veces la contraseña?
La cuenta se bloquea 15 minutos. Pasado ese tiempo puede intentar de nuevo; si no recuerda la contraseña, pida el restablecimiento.

¿Puedo usar Excel para editar el inventario?
Puede exportar a CSV para analizar, pero la edición oficial se hace en el sistema; no vuelva a importar el CSV sin un procedimiento definido.

¿El sistema monitorea la red en tiempo real?
No. Solo guarda el inventario y los mantenimientos. Para monitoreo se requiere una herramienta como SNMP/Zabbix.

¿El sistema configura los routers?
No. Genera la configuración y un plan de pruebas; el cambio se aplica manualmente en Packet Tracer o en el equipo.

¿Qué hago si la API no responde?
Verifique la dirección, la VPN y el servicio; si persiste, avise a soporte con la hora y el mensaje.

¿Puedo compartir mi usuario?
No. Cada acción queda registrada a nombre de la cuenta; compartirla rompe la trazabilidad y la seguridad.
