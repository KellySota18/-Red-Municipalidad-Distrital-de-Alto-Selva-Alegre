2. Descripción técnica de la solución

2.1 Objetivo del sistema

Implementar una plataforma que permita inventariar la red municipal, gestionar mantenimientos, administrar usuarios con roles y probar las ACL de los routers antes de aplicarlas, con autenticación, autorización, auditoría y copias de seguridad cifradas.

2.2 Tipo de aplicación

Es una solución cliente-servidor de tres capas con cliente de escritorio por consola:

Capa Implementación
Presentación PowerShell 5.1/7 con el módulo RedCli.psm1; no hay interfaz web ni móvil
Aplicación API REST en Node.js 20 + Express 4
Datos PostgreSQL 16, base infra_red_db, esquema infra
Herramientas complementarias Simulador/generador de ACL en Node.js y Cisco Packet Tracer
Operación Copias de seguridad cifradas con pg_dump + GnuPG

2.3 Principales componentes

Componente Archivo / ubicación Función
Esquema de base de datos bd/infra_red_schema_seguro.sql Tablas, tipos, roles, RLS, auditoría, funciones de autenticación
Datos del Diario bd/seed_datos_municipalidad.sql Ubicaciones, VLAN, subredes y dispositivos iniciales
Extensión ACL bd/infra_red_acl_extension.sql Políticas, ACL, reglas, aplicaciones y pruebas
Datos de ACL bd/seed_acl_informe.sql, bd/seed_acl_reglas.sql, bd/seed_pruebas_simulador.sql Routers, políticas P1–P8, ACL v1/v2 y resultados
API api/server.js Autenticación, inventario, mantenimientos, usuarios, seguridad
Dependencias de la API api/package.json, api/package-lock.json Express, pg, zod, helmet, cors, cookie-parser, express-rate-limit
Configuración de entorno api/.env (no versionado) Cadena de conexión, orígenes permitidos, puerto, TLS
Consola de usuario RedCli.psm1 Comandos Connect-Red, Get-RedDispositivo, etc.
Herramientas ACL acl/*.js Simulación, generación de configuración y plan de pruebas
Configuraciones de routers acl/config/*.cfg Configuraciones v1 y v2 para R1 y R1B
Respaldos scripts/backup.ps1, scripts/probar_restauracion.ps1, scripts/backup_postgres.sh Copia cifrada, verificación y restauración
Documentación de seguridad docs/guia_seguridad.md Controles, pruebas y hallazgos

2.4 Arquitectura general

Figura 1. Arquitectura general: usuarios → consola PowerShell → API REST → PostgreSQL. Los administradores usan pgAdmin y las herramientas ACL; las copias se cifran con GPG.

Flujo de una operación típica:

  1. El usuario ejecuta un comando en PowerShell (Get-RedDispositivo).
  2. RedCli.psm1 envía una solicitud HTTP a la API con la cookie de sesión.
  3. La API valida la solicitud con zod, comprueba la sesión y el token CSRF.
  4. La API abre una transacción en PostgreSQL, fija app.user_id y ejecuta una consulta parametrizada.
  5. PostgreSQL aplica RLS y devuelve solo las filas permitidas.
  6. La API responde en JSON; la consola lo presenta como tabla o lista.
  7. La operación de escritura queda registrada en infra.auditoria.

2.5 Interacción entre componentes

Interacción Protocolo Puerto Observación
Consola → API HTTP en desarrollo; HTTPS en producción 3000 local / 443 público La API escucha solo en 127.0.0.1
API → PostgreSQL TCP PostgreSQL 5432 Solo desde el servidor de la API
pgAdmin → PostgreSQL TCP PostgreSQL 5432 Solo desde la red administrativa
API → servicios externos No requiere — No hay dependencia de servicios de terceros en tiempo de ejecución
Respaldo → almacenamiento Sistema de archivos / red — pg_dump cifrado con GPG
Herramientas ACL → routers Consola / Packet Tracer — La configuración se aplica manualmente

Figura 2. Despliegue local y en servidor institucional: proxy inverso con TLS, API en localhost, PostgreSQL en localhost y respaldos externos.

2.7 Decisiones de diseño y seguridad

  • Sin acceso directo a la base desde la consola: todo pasa por la API, que valida y parametriza las consultas.
  • Roles de base de datos de mínimo privilegio: app_backend pertenece a rol_app; no es superusuario y no puede leer usuarios, sesiones ni auditoria.
  • RLS: la base deduce el rol desde app.user_id; no confía en un rol enviado por el cliente.
  • Contraseñas: bcrypt con costo 12; nunca se almacenan en claro ni se devuelven por la API.
  • Sesiones: token de 256 bits; en la base solo se guarda su SHA-256; expiración absoluta de 8 h e inactividad de 30 min.
  • CSRF: cookies SameSite=Strict, verificación de Origin y token de doble envío.
  • CORS: lista blanca explícita; nunca * con credenciales.
  • Rate limit: 120 solicitudes/min por IP en la API y límites de login en la base.
  • Auditoría inmutable: triggers en las tablas principales; UPDATE, DELETE y TRUNCATE sobre auditoria están bloqueados.
  • Secretos: solo en variables de entorno o gestor de secretos; .env está en .gitignore.

4.6 Variables de entorno

La API se configura con un archivo .env que no se versiona. Nunca incluya secretos reales en este manual ni en el repositorio.

Variable Obligatoria Ejemplo Descripción
DATABASE_URL Sí postgres://app_backend:CAMBIAR@localhost:5432/infra_red_db Cadena de conexión de la API

NODE_ENV=development
PORT=3000

DATABASE_URL=postgres://app_backend:REEMPLAZAR_POR_SECRETO@localhost:5432/infra_red_db
ALLOWED_ORIGINS=https://red.altoselvaalegre.gob.pe
NODE_ENV=production
PGSSL=0
TRUST_PROXY=1
PORT=3000

Sobre PGSSL: use 1 solo si PostgreSQL está configurado con TLS y la API tiene el certificado correspondiente. Si la API y la base están en el mismo servidor y no se configuró TLS en PostgreSQL, use 0; de lo contrario, la conexión fallará.

4.8 Requisitos de red y conectividad

  • El servidor debe tener IP fija o reserva DHCP.
  • El cliente debe resolver el nombre del servidor (DNS interno) o usar la IP.
  • La API debe poder conectarse a PostgreSQL por localhost o por la red interna.
  • El puerto 443 debe estar abierto solo desde las redes autorizadas.
  • El puerto 5432 no debe estar abierto a Internet.
  • Si se usa correo o nube para respaldos, habilitar solo las salidas necesarias.
  • Sincronizar la hora del servidor (NTP) para que sesiones, auditoría y TLS funcionen correctamente.

4.10 Credenciales y secretos

  • No se incluyen contraseñas, tokens, claves privadas ni credenciales reales en este documento.
  • Cada entorno debe tener su propio secreto.
  • Use un gestor de secretos o variables de entorno; no escriba secretos en .sql, .js, .md ni en Git.
  • Rote el secreto de app_backend si sospecha que se filtró.
  • El archivo .env debe tener permisos restringidos al usuario que ejecuta la API.

5.5 Creación y configuración de la base de datos

Paso 1: crear la base

cd C:\proyecto_red\bd
psql -U postgres -c "CREATE DATABASE infra_red_db;"

Resultado esperado: CREATE DATABASE.

Paso 2: cargar los scripts en orden

$orden = "infra_red_schema_seguro","seed_datos_municipalidad","infra_red_acl_extension","seed_acl_informe","seed_acl_reglas","seed_pruebas_simulador"
foreach ($f in $orden) {
  Write-Host "== $f"
  psql -U postgres -d infra_red_db -v ON_ERROR_STOP=1 -q -f "$f.sql"
  if ($LASTEXITCODE -ne 0) { Write-Host "FALLO $f" -ForegroundColor Red; break }
}

Resultado esperado: se muestran los seis nombres y no aparece ningún mensaje FALLO. Cada archivo corre en una transacción; si uno falla, no deja cambios a medias.

Evidencia de consola:

Figura 4. Carga correcta del esquema, datos y ACL, con los conteos esperados.

Paso 3: verificar los datos iniciales

psql -U postgres -d infra_red_db -Atc "SELECT 'dispositivos='||count(*) FROM infra.dispositivos UNION ALL SELECT 'subredes='||count(*) FROM infra.subredes UNION ALL SELECT 'acls='||count(*) FROM infra.acls UNION ALL SELECT 'reglas='||count(*) FROM infra.acl_reglas UNION ALL SELECT 'pruebas='||count(*) FROM infra.pruebas_conectividad"

Resultado esperado:

subredes=8
acls=16
reglas=127
pruebas=55

Si los valores no coinciden, no continúe: revise el orden de los scripts y vuelva a ejecutar el que falló.

5.6 Creación del primer administrador

No hay registro público. El primer administrador se crea con la función infra.registrar_usuario, que solo puede ejecutar el DBA.

$sql = @'
SELECT infra.registrar_usuario('Tu Nombre', 'tu_correo@dominio.pe', 'Cambia-Esta-Clave-2026!', 'administrador');
'@
$sql | psql -U postgres -d infra_red_db -At

Resultado esperado: un UUID, por ejemplo e03a2c3e-e06d-4735-847c-ed7a1528b9b4.

Reglas de la contraseña:

  • 12 o más caracteres.
  • Al menos una mayúscula, una minúscula, un número y un símbolo.
  • Máximo 72 bytes.
  • No use la contraseña de ejemplo. Use una propia, única y guárdela en un gestor de contraseñas.
  • Evite la letra Ñ y el símbolo $ si la consola tiene problemas de codificación.

Importante: Cambia-Esta-Clave-2026! es solo un ejemplo. Reemplácela antes de ejecutar. Si la contraseña no cumple la política, la base responde con un error y no crea el usuario.

5.7 Creación de la cuenta de la API

La API se conecta con un usuario de base de datos de mínimo privilegio, no con postgres.

$b = New-Object byte[] 32
[Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b)
$pw = ($b | ForEach-Object { $_.ToString('x2') }) -join ''
$sql = "CREATE ROLE app_backend LOGIN PASSWORD '$pw' IN ROLE rol_app CONNECTION LIMIT 20; ALTER ROLE app_backend SET statement_timeout='5s'; ALTER ROLE app_backend SET idle_in_transaction_session_timeout='15s';"
$sql | psql -U postgres -d infra_red_db

Resultado esperado: CREATE ROLE y ALTER ROLE.

Importante: deje abierta esa ventana de PowerShell porque la variable $pw se usa en el paso 5.9. Si cierra la ventana, deberá restablecer la contraseña con:

$sql = "ALTER ROLE app_backend PASSWORD 'NUEVO_SECRETO_GENERADO';"
$sql | psql -U postgres -d infra_red_db

Verificar los roles:

psql -U postgres -d infra_red_db -c "\du"

Resultado esperado: aparecen postgres, rol_app, app_backend y rol_lectura.

5.10 Ejecución de migraciones y scripts iniciales

El proyecto no usa un sistema de migraciones automático: los scripts SQL son la migración. Ya se ejecutaron en 5.5. Para volver a aplicarlos, son re-ejecutables y no duplican datos.

Si cambió las ACL y desea regenerar los SQL:

6.5 Despliegue en un servidor remoto o plataforma en la nube

Requisitos previos:

  • Una VM con Windows Server o Linux.
  • Un nombre DNS, por ejemplo red.altoselvaalegre.gob.pe.
  • Un certificado TLS válido para ese nombre.
  • Reglas de firewall y grupo de seguridad.
  • PostgreSQL instalado en la misma VM o en una instancia gestionada.

Pasos generales:

  1. Crear la VM y abrir solo los puertos 443 (público) y 22/3389 (administración restringida).
  2. Instalar PostgreSQL 16 y Node.js 20.
  3. Copiar el proyecto y ejecutar la instalación (sección 5).
  4. Configurar .env de producción.
  5. Instalar y configurar Nginx, Caddy o IIS como proxy inverso con TLS.
  6. Registrar la API como servicio.
  7. Configurar el firewall del sistema operativo y el grupo de seguridad.
  8. Configurar DNS para que apunte a la IP pública.
  9. Verificar el acceso por HTTPS.
  10. Programar respaldos y copiarlos a un almacenamiento externo.

Ejemplo de configuración de Nginx (Linux):

server {
    listen 80;
    server_name red.altoselvaalegre.gob.pe;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name red.altoselvaalegre.gob.pe;

    ssl_certificate     /etc/ssl/certs/red_altoselvaalegre.crt;
    ssl_certificate_key /etc/ssl/private/red_altoselvaalegre.key;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;

    add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
    add_header X-Content-Type-Options "nosniff" always;
    add_header X-Frame-Options "DENY" always;

    location / {
        proxy_pass         http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_read_timeout 30s;
    }
}

sudo nginx -t
sudo systemctl reload nginx

Resultado esperado: nginx: configuration file ... test is successful y el acceso HTTPS responde.

Notas para IIS:

  • Instalar el módulo Application Request Routing (ARR) y URL Rewrite.
  • Crear un sitio con enlace HTTPS y certificado válido.
  • Configurar una regla de proxy inverso hacia http://127.0.0.1:3000.
  • Definir TRUST_PROXY=1 en .env.
  • No habilitar la exposición directa del puerto 3000.

Notas para Caddy (alternativa simple):

red.altoselvaalegre.gob.pe {
    reverse_proxy 127.0.0.1:3000
}

Caddy obtiene y renueva el certificado TLS automáticamente si el dominio es público.

10.2 Copia de seguridad

powershell -ExecutionPolicy Bypass -File C:\proyecto_red\scripts\backup.ps1 -Destinatario backup@red.local

Genera:

C:\backups\infra_red_db_AAAAMMDD_HHMMSS.dump.gpg
C:\backups\infra_red_db_AAAAMMDD_HHMMSS.dump.gpg.sha256

La copia se cifra en la tubería: el volcado no queda en claro en el disco. La rotación elimina las copias de más de 30 días.

10.3 Restauración de prueba

powershell -ExecutionPolicy Bypass -File C:\proyecto_red\scripts\probar_restauracion.ps1

El script verifica el SHA-256, descifra, crea una base temporal, restaura, cuenta filas y elimina la base temporal. No sobrescribe la base de producción.

10.4 Restauración real

  1. Detener la API.
  2. Crear una base nueva o respaldar la actual.
  3. Descifrar la copia:

powershell gpg --batch --yes --output C:\backups\restauracion.dump --decrypt C:\backups\infra_red_db_AAAAMMDD_HHMMSS.dump.gpg

  1. Restaurar:

powershell pg_restore -U postgres -d infra_red_db --no-owner --exit-on-error C:\backups\restauracion.dump

  1. Verificar conteos y probar la API.
  2. Eliminar el archivo descifrado de forma segura.
  3. Registrar el incidente y la restauración en la bitácora.

Anexo D. Operaciones administrativas del DBA

Solo para el DBA. No ejecute estas operaciones desde la consola de usuario. Reemplace los valores entre <> y no use contraseñas reales en documentos.

D.1 Restablecer una contraseña y desbloquear una cuenta

UPDATE infra.usuarios
   SET contrasena_hash = extensions.crypt('<Nueva-Clave-2026!>', extensions.gen_salt('bf', 12)),
       intentos_fallidos = 0,
       bloqueado_hasta = NULL
 WHERE email = '<usuario@dominio.pe>';

UPDATE infra.sesiones
   SET revocada = true
 WHERE id_usuario = (SELECT id_usuario FROM infra.usuarios WHERE email = '<usuario@dominio.pe>')
   AND NOT revocada;

D.2 Cambiar el rol de un usuario

UPDATE infra.usuarios
   SET rol = '<consulta|tecnico|administrador>'
 WHERE email = '<usuario@dominio.pe>';

D.3 Desactivar una cuenta

UPDATE infra.usuarios SET activo = false WHERE email = '<usuario@dominio.pe>';
UPDATE infra.sesiones SET revocada = true
 WHERE id_usuario = (SELECT id_usuario FROM infra.usuarios WHERE email = '<usuario@dominio.pe>')
   AND NOT revocada;

D.4 Reactivar una cuenta

UPDATE infra.usuarios SET activo = true WHERE email = '<usuario@dominio.pe>';

D.5 Consultar la auditoría de un usuario

SELECT fecha, tabla, operacion, id_registro, datos_antes, datos_despues
  FROM infra.auditoria
 WHERE id_usuario_app = (SELECT id_usuario FROM infra.usuarios WHERE email = '<usuario@dominio.pe>')
 ORDER BY fecha DESC
 LIMIT 50;

D.6 Verificar la postura de las ACL

SELECT router, version, acl, postura
  FROM infra.v_acl_postura
 ORDER BY version, router, acl;
